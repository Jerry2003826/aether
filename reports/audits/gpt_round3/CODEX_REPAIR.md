## 必需修改

### R3-01 当前验证不能返回已失效历史 PASS

先验证正常产物，再损坏同一 ID/同一合同的字节，再次验证；以及正常后 tombstone、来源删除。当前三个用例都复用旧 PASS。

将历史证据查询与当前重新验证分开。读取当前候选、可见性、所需来源，任何当前失败不能被缓存覆盖。身份绑定包括候选/批准合同/验收器或可信套件版本/必要来源快照。不要修改旧证据来伪装当时失败。补先 FAIL 后修好、重复有效检查、并发复验与验证—终态间删除的测试。

### R3-02 真正的目标与合同验收

默认执行现在只取第一行足够长的来源，出现任意引用就 SUCCEEDED。资料中有维护周期与 API 限额，问限额却答维护周期，仍成功；算术目标同样被无关摘录标成功。

不要硬编码六十次/391。固定摘录只可作为显式受限能力/离线工程探针；不适用的目标给 NEEDS_REVIEW/UNVERIFIABLE。连接已有 typed loop、网关、工具与独立 verifier，按批准合同对真实产物验收。没有 key 可以跑明确的 scripted provider，但要区分“工作流运行通过”和“用户目标完成”。

验证者自己读权威合同内容和摘要，不能只保存调用方给的 contract_sha。若输入哈希与权威合同不符应拒绝；处理 active/current contract 与旧历史，不能默认取最早一版。上线 live 前检查 create_task 中 budget/allowed_source_ids 是否被保留和执行；未支持时拒绝字段，不能静默丢弃。

### R3-05 暂停/取消与状态一致性

PAUSED 必须阻止新执行/新副作用。明确 Workflow 的 pause/resume/cancel 语义，不能所有命令最终都进只接受 start 的函数被 ignored。条件状态更新必须检查 rowcount；更新失败不得返回与数据库相反的 SUCCEEDED。

用公开 HTTP 命令启动、暂停、恢复、取消；在真实执行期间测试，不只在 sleep 停进程。对已经开始的外部操作按可取消/待对账处理，不把取消当回滚。

### R3-03 内容去重与任务引用分离

同一来源两次任务会生成同一答案，put 返回同一 artifact ID，第二任务绑定 UPDATE 0 行。两任务都成功但第二任务没有答案。

保留共享 blob，增加正确的逻辑产物/任务关联及迁移。按授权关系更新 API artifact_ids 查询和验证绑定。不得覆盖首任务 task_id，不得给输出加随机垃圾绕过去重。补重试、并发、相同内容不同用途/分类、跨项目隔离和删除关联的检查。

### R3-04 追加和恢复使用同一日志一致性协议

先写完整 staged 记录 + 截断尾，再正常上传新文件，然后 recover。当前会变成中间行损坏。追加前或有强制栅栏的启动流程应修复尾部，不能寄希望于用户先手动恢复。

恢复时保留完整前缀，不先 truncate(0) 再回写。把坏尾隔离并同步后，截到完整前缀字节位置。锁须覆盖追加/修复；若替换文件，使用稳定独立锁避免 inode 变化。保留中间真损坏的报错；测试修复期间二次失败。不得异常吞掉返回空列表当作成功。
